# 技能壳（thinking-space/shells）

把思维空间的技能注册成工具入口的固定子插件。

**它不生成任何程序文件。** 程序在这里一次写好、随包发布；运行时只往自己的 `data/shells.json` 里记一条，按记录调用 `ctx.tools.register()` 把工具挂出去，删的时候注销。

## 为什么改成一个固定插件

上一版是「每个壳一个子插件目录」：加壳要往 `sub/` 写 `index.ts` 和 `plugin.yaml`、改父插件 `plugin.yaml` 的 `sub:`、调 `POST /api/plugin` 重载、再拿 `/api/status` 和探针核对。那条路上每一步都会留下半成品：

- 重载断线后不知道新代码上没上 → "待确认"卡住
- 删了目录、记录还在 → 点开 404 的幽灵页
- 写一半的目录、备份、回滚、墓碑

宿主对运行时改写程序文件也有明确要求（issue #9 第 19 条）：运行时生成的东西留在插件数据目录，通过公开接口提供调用。

现在壳是固定的程序，记录落在 `data/shells.json`。加一条就注册一个工具，删一条就注销一个，**立刻生效，不用重载**。

## 它做什么

每个壳对应一条技能。工具被调用时：

1. 用调用者的权限（`session.permission`）去调 `space_run`，不写死
2. 危险等级只决定「要不要问」。放行条件记在壳自己这条记录的 `approval` 上，两档：

   - `ask`（默认）——**每次执行都要当次的明确同意**。壳去问宿主审批接口（`ctx.approval.request()`），拿到 `approved` 才把 `confirmSideEffects` 传 `true`。宿主现在没有审批流，所以它停在 `needs_confirmation`，一次也不调 `space_run`。
   - `full`——**事先的持续授权**。用户在壳页面上把这一条改成 full，等于说「这个壳以后含副作用的步骤直接跑，不用再问」。之后每次调用都按 full 权限执行，不再经过审批接口。

   `full` 不是「这一次同意」，也不看调用者所在会话是什么权限；它是针对这个壳的长期决定，随时可以在页面上改回 ask。

   还有一道事后的闸：每次执行前重新读一次技能的权限声明，和记录里的 `requiredPermission` 比对，变了就 `blocked`，请人删旧壳重新发布。这道拦的是「声明被换掉」，拦不住「声明没变但内容被改得更危险」——那要你自己信得过这条技能。
3. 把 `space_run` 的回执原样转述，包括 `staleDefinition`（技能在运行期间被改过）

危险等级**从技能自己声明的步骤推导**，页面加壳时直接读 `space_skills` 返回的 `danger`，壳不能自己填。

推导时有两种「说不清」，都按 `ask` 处理，不落到 `safe`：一是工具在目录里、但它的 `danger` 缺失或不是已知值（视为「未知」）；二是那一步的工具此刻不在工具目录里（拿不到等级，只能按旧值算，而旧值是 `safe` 时抬到 `ask`）。已经确认的 `full` 不会被降级。

## 代价

加壳不是免费的，这几条都是真的：

| 代价 | 说明 |
|---|---|
| 每轮付 token | 一个壳就是一个常驻工具，工具定义每轮请求都发，不用也付 |
| 共用一个进程 | 所有壳都在这个子插件里，它挂了壳一起没（以前一个壳一个子插件，崩一个不连坐） |
| 参数变更要重载 | 加壳删壳立刻生效；技能自己改了参数声明，得重载子插件才跟上 |
| 依赖未成文能力 | 「apply 之后注册工具」实测可用，但没写进插件契约；收紧就要重做 |
| 技能与壳不同步 | 技能删了壳还在，一调就失败；技能改版本，壳不会自动重注册 |

**只在两种情况下值得加壳**：这条技能必须每轮被模型看见（不搜就想不到），或者要交给别人用。
一次性的、只自己偶尔用的，直接 `space_run` 就行。

## 数据文件

```json
{
  "schemaVersion": 1,
  "items": [
    {
      "skillId": "test-comfy-two-step",
      "toolName": "skill_test_comfy_two_step",
      "label": "测试·出图两段",
      "danger": "safe",
      "requiredPermission": "safe",
      "approval": "ask",
      "skillRevision": 2,
      "enabled": true,
      "addedAt": "2026-11-23T14:35:46.867Z"
    }
  ]
}
```

工具名按技能 id 生成（非字母数字转下划线，长度 60），撞了自动加 `_2`。

- `requiredPermission`：加壳时从技能声明抄下来的原始权限要求，执行前拿它跟当前技能再比一次。
- `approval`：`ask` / `full`，默认 `ask`。写 `full` 就是这一条壳的持续授权，见上面「它做什么」第 2 条。
- 老记录缺 `requiredPermission` 时，启动会按技能当前声明补一次；技能已经读不到就补不上，那条壳一调就 `blocked`。

## 页面

`/plugins/thinking-space/shells/`（设置页），列出当前壳、从技能列表里挑一条加壳、删除壳，每条壳有一列「免问」可以选 `ask` / `full`。加壳时如果技能不存在或已有壳会直接说原因；技能没有权限声明时直接拒，不默认成 `safe`。

## 不读别的插件的文件

技能目录靠 `ctx.tools.call("space_skills", {}, { permission: "ask" })` 问，这是公开的工具接口。不 `existsSync` 别人的目录，不猜路径，不读宿主 `config.json`。

> 注意 `permission` 只接受 `off | ask | full`。传别的值（比如 `safe`）会被当成"需要审批"，M0 宿主没有审批流，直接失败。

## 依赖

`depends: [web, tools]`。不需要写 `comfy` 这类具体插件——壳只依赖 `space_run` 和 `space_skills`，那是父插件的工具，不是别的插件的服务。缺工具时会在运行时报出来，不会拦住加载。

## 已知边界

- 工具重名会抛错（宿主 `add()` 里 `entries.has(name)` 直接 throw）。所以更新一条壳要先注销再注册，代码里 `syncRegistrations()` 按 skillId 管理 disposer 就是这个原因。
- 重载父插件会连带重启这个子插件，正在跑的调用会断——那是宿主的生命周期，不是这里能控制的。
- `enabled: false` 的记录不注册工具，记录还在。
